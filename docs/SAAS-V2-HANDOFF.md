# SaaS V2 implementation handoff

Target repository: `bcameron812/NotTheRealApi`. This CLI phase changes no SaaS source, migrations, hosted sessions or flags. CLI **0.2.0 is an unpublished candidate**. Current hosted Stripe V1 remains the compatible path. Production remains disabled unless separately approved.

## Contract to implement

Use [listener-protocol-v2.md](listener-protocol-v2.md), [protocol-v2.schema.json](protocol-v2.schema.json), [fixtures/v2.json](fixtures/v2.json) and the exported `/protocol-v2` runtime validators as the exact contract. The generated schema requires the additional runtime checks listed in its `$comment` and the protocol document. Pin the CLI commit and archive SHA-256 used for acceptance.

1. Keep existing `/listener/v1/*` routes and `ntapi.listener.v1` strict schemas unchanged. They continue emitting only the existing Stripe format. Add strict `/listener/v2/*` POST registration/renewal, claim, ACK and close routes with `ntapi.listener.v2` in every request, response and error, and the matching version header. Reject path/header/body mismatches; never infer a version from provider or payload. CLI selection is explicit, defaults to V2, and legacy requires `--protocol v1`; there is no negotiation endpoint or downgrade signal in this release. Do not reinterpret V1 errors as capability advertisements.
2. In `src/server/listener/protocol.ts`, separate V1 and V2 schema exports. V2 retains all V1 identity, scope, session, lease, generation, body and outcome constraints; adds required `method:"POST"`; replaces the three-header Stripe rule with generic bounded pairs; adds optional `verificationUrl`. Consult the exact denylist and bounds in the protocol. Keep `scope.module`, event type, environment and provider metadata independent of header validation. There is no CLI provider field or registry.
3. In the service/management/claim paths, persist the session's delivery version or derive it from durable versioned identity safely. Scope all user/workspace/environment/module/destination and action checks to the grant on every operation. Validate revocation, expiry, route ownership, entitlement and feature gates before granting any claim, retry receipt, ticket or close. Share the **one-active-listener-per-user constraint across V1 and V2**, not one per version. Do not weaken fencing on upgrade.
4. Build V2 deliveries from the saved **actual signed outbound bytes and headers**, not parsed payloads and not a fresh signing operation. Store canonical Base64, byte count and SHA-256 together. The controlled provider lifecycle/delivery policy selects provider-generated signature/auth/timestamp/correlation/entity headers and permitted custom headers. Apply the generic CLI safety rules server-side too; reject forbidden/conflicting headers, never silently truncate or omit encoding metadata. Standard Webhooks needs `webhook-id`, `webhook-timestamp`, `webhook-signature` and optional Content-Type; four pairs fit naturally. A registered Dataverse custom auth header is admissible; generic Authorization/Cookie remain forbidden. Do not forward original caller credentials into the local receiver.
5. Obtain `verificationUrl` from the saved canonical public destination actually passed to the signer. Canonicalize to the documented exact HTTPS serialization **before signing**, store it with the delivery, and preserve query ordering/encoding. No original caller Host, X-Forwarded-* or arbitrary metadata may establish this value. Never replace it with the CLI target, put it in ACK evidence or routine logs, or use it to route a listener delivery. CLI disclosure to its local receiver is opt-in and namespaced; provider header emission must reject the entire `x-ntapi-listener-*` namespace. Handle old noncanonical signing URLs before enabling URL-bound fixtures; do not normalize after signing.
6. Preserve atomic one-outstanding-claim behavior, unique attempt IDs for each execution/redelivery, increasing fencing generations, capability ownership and session-bounded leases. Lost claim replies replay **the identical claim**, including bytes, headers, URL and lease. Expired claims cannot authorize execution. ACKs record complete evidence durably under an idempotency key; identical ACK retries return the original receipt, changed ACKs are rejected, stale capabilities/generations are fenced. Do not mark success at claim/download or receipt time. Keep current bounded scheduling/retention/poison policy; no client spool is added.
7. Keep notification version/routes/ticket/frame schema unchanged. Ticket issuance resolves either stored delivery version to the same authorized session. WS upgrade/frames remain credential-free hints (the first subscribe frame redeems the opaque single-use ticket, as before). HTTPS registration/claim/ACK/close remains authoritative. Keep healthy idle probes within 60 seconds and fallback behavior. V2 support does not require a gateway/Redis redesign.

Prefer existing durable columns/model relationships where they already store version and signing input. Generate a migration **only if** an actual model alteration is required; document the need and use the SaaS migration/review process. This handoff does not authorize a speculative migration.

## Enablement and UI

Review `PROVIDER_LIFECYCLES`: Twilio, HubSpot, Dataverse and OpenAI are currently HTTPS-only; add listener delivery capability only after their actual V2 emission and independent Preview acceptance exist. Meta stays polling-only. Keep Stripe V1 available. The hosted service must not advertise V2/non-Stripe support merely because the CLI accepts it.

Update listener UI, management routes, grant issuance and hosted test harness together: show the correct explicit wire command, module/environment scope, fixed local destination binding and provider verification instructions. Explain public signing URL versus local receiver; URL-bound verifiers need `--include-verification-url`. Do not display synthetic secrets/signing query strings by default. Provider policy changes within the envelope are server changes; no CLI update instruction is needed. The service's capability declarations must reflect deployed, tested functionality.

## Preview acceptance after implementation

Request separate owner authorization for SaaS changes/deployment/hosted testing. Build and record the **exact deployed Preview SHA**, CLI commit, tarball hash, hosted feature flags, synthetic grant scope/expiry and fixture IDs. Use the built tarball installed in a fresh consumer, not source imports. A locally passing reference server is necessary but cannot establish hosted compatibility.

For Stripe plus each of Twilio, HubSpot v3, Dataverse registered header auth and OpenAI Standard Webhooks, run actual **Preview HTTPS → packaged CLI → real loopback receiver → Preview HTTPS ACK**. Independently verify using SDK/oracle at the receiver with synthetic signing material. Include UTF-8, binary/non-JSON where applicable, form field encoding, Standard Webhooks' three headers and a canonical public URL with path/query. For URL-bound providers, verify correct URL succeeds and changed path/query/localhost fails. Confirm no provider headers/keys, signing URLs or response content leak to logs or ACK evidence.

Exercise duplicate/redelivery and retry, identical lost claim reply, ACK response loss, changed ACK, stale generation, lease/session expiry, competing V1/V2 sessions, wrong module/environment/destination, revoked/closed grants, local 500, timeout/disconnect uncertainty, healthy WS idle/resync and HTTPS fallback. Capture sanitized evidence that ACK is recorded outcome rather than local success. Introduce a fresh fictional header set solely in server fixtures and prove the unchanged CLI accepts it while refusing forbidden transport headers before local I/O.

Every hosted result must be bound to the exact deployed SHA and active flags; rerun when the deployment changes. Remove all synthetic fixtures/grants/sessions and verify cleanup. Do not use real provider accounts or Production traffic for this gate. Keep Production disabled pending separate owner approval.

## Upgrade and rollback

Deploy dual-stack V1/V2 support to separately authorized Preview first, with non-Stripe listener capabilities disabled. Verify unchanged V1 clients, including published 0.1.0. Enable one implemented provider capability at a time only for synthetic authorized Preview acceptance; advertise only successful capabilities. Retain V1 throughout. Once approved for users, V2 users select the default command; existing V1 users explicitly select `--protocol v1` until their service is upgraded. Never silently change an active session's wire version.

For rollback, stop advertising/issuing V2 listener capabilities and stop new V2 session creation, fence or drain outstanding V2 leases under the existing TTL/retention rules, and retain durable ACK/idempotency records so response-loss retries remain truthful. If V2 routes cannot remain during draining, report terminal version/availability failures and document uncertain local effects; never convert outstanding V2 claims to V1. Keep V1 Stripe service and explicit legacy CLI mode available. Roll back any real durable model change only under its separately reviewed migration plan; retain needed evidence. Production enablement, flags, release/tag and npm publication are separate owner decisions.

The CLI release gate is [provider-agnostic-contract](../test/provider-agnostic-contract.test.mjs), also exercised against the installed archive by `pack:smoke`. No provider-specific CLI patch is permitted for an ordinary callback within V2 bounds. Capabilities outside these bounds require a reviewed new transport design.
